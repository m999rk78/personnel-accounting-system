# Selectel + Coolify

Целевой production-контур не зависит от Yandex Cloud:

```text
GitHub → Coolify (Mark's Team) → отдельный сервер Selectel
                                    ↓ приватная сеть
                             Managed PostgreSQL 18
```

Все ресурсы создаются в отдельном проекте Selectel **Personnel Accounting**.
Ресурсы проекта миграции `welding-journal` использовать или изменять нельзя.

## Рекомендуемая конфигурация

- отдельная приватная сеть и подсеть для приложения и базы;
- сервер приложения: Ubuntu LTS, 2 vCPU, 4 ГБ RAM, SSD 40 ГБ;
- Managed PostgreSQL 18: одна нода, база `personnel`, пользователь `personnel`;
- полная резервная копия раз в неделю и ежедневные инкрементальные копии,
  хранение 7 дней;
- прямой публичный IP только у сервера приложения;
- PostgreSQL доступен только из приватной подсети;
- Coolify подключается к серверу отдельным SSH-ключом проекта;
- приложение разворачивается из `Dockerfile`, без локального PostgreSQL из
  `docker-compose.yml`; служебный том режима обслуживания описан ниже.

## Переменные Coolify

Значения пароля, сертификата, webhook и почтового ключа хранятся как secrets.

```dotenv
NODE_ENV=production
HOST=0.0.0.0
PORT=8080
PGHOST=master.d9725049-e1dd-492c-9a1e-81b4f96aa767.c.dbaas.selcloud.ru
PGPORT=5432
PGUSER=personnel
PGPASSWORD=<secret>
PGDATABASE=personnel
DATABASE_SSL=verify-full
DATABASE_CA_CERT=<корневой сертификат Selectel с \n вместо переносов строк>
DATABASE_POOL_SIZE=5
APP_ORIGIN=https://uchet-personala.ru
PUBLIC_APP_ORIGIN=https://uchet-personala.ru
BITRIX24_SYNC_ENABLED=false
MAIL_PROVIDER=yandex-postbox
MAIL_FROM=no-reply@uchet-personala.ru
YANDEX_POSTBOX_API_KEY_ID=<secret>
YANDEX_POSTBOX_API_KEY_SECRET=<secret>
```

Проверка состояния контейнера: `GET /api/health`. Она возвращает `200`, только
когда приложение может выполнить запрос к PostgreSQL. При запуске контейнер под
advisory lock применяет миграции из `drizzle-postgres`, затем запускает сервер.

## Порядок запуска

1. Создать новые сеть, сервер и PostgreSQL 18 в проекте `Personnel Accounting`.
2. В Coolify выбрать только `Mark's Team` и добавить новый сервер отдельным
   SSH-ключом.
3. Создать новое приложение из репозитория и выбрать сборку из `Dockerfile`.
4. Добавить переменные, но оставить синхронизацию Bitrix24 выключенной.
5. Первый деплой выполнить на временном домене Coolify.
6. Проверить `/api/health`, вход, справочники, отчёты и табели.
7. Переключить `uchet-personala.ru` только после проверки временного адреса.
8. Включать Bitrix24 и загружать рабочие данные отдельным решением после запуска.

Локальный `docker-compose.yml` нужен только для разработки и проверки. Он
использует отдельный PostgreSQL 18 и не участвует в production-развёртывании.

## Технические работы и безопасная замена контейнера

Эти настройки относятся к существующему приложению `personnel-accounting` /
`production` команды `yums` (прежнее название — `Mark's Team`) на сервере
`personnel-accounting-app`. Текущие домены — `resurs-otchet.ru` и
`www.resurs-otchet.ru`. Новые серверы и базы не нужны; другие проекты, DNS и
почтовые записи не изменяются.

### Поведение приложения

Production-вход на порту `8080` обслуживает небольшой gateway. Он начинает
отвечать до миграций: страницы получают автономный экран технических работ,
API — JSON с `503`, `Retry-After` и кодом `MAINTENANCE`. После миграций и
успешной проверки PostgreSQL gateway открывает приложение. Внутренний backend
слушает только `127.0.0.1:8081`, управление — `127.0.0.1:8082`; эти порты
не публикуются.

Уже открытая вкладка показывает модальный экран поверх приложения. Таблицы и
редакторы остаются смонтированными. Восстановление связи снимает экран без
перезагрузки и повторной отправки записей. Ввод сохраняется, пока вкладка
остаётся открытой; хранение кадровых данных в `localStorage` не добавляется.
Сохранения с потерянным ответом автоматически не повторяются: результат может
уже находиться в БД, его нужно проверить перед повторной отправкой.

### Постоянный переключатель и команды деплоя

До включения автоматических команд подключить к приложению постоянное хранилище
на `/app/.runtime`. Оно должно быть одним и тем же у текущего и нового
контейнеров и доступно на запись пользователю `1001:1001`. Это небольшой файл
состояния, не новая база. Без общего хранилища новый контейнер не увидит
переключатель предыдущего.

Переменные без секретов:

```dotenv
MAINTENANCE_STATE_FILE=/app/.runtime/maintenance.json
MAINTENANCE_DRAIN_TIMEOUT_MS=120000
MAINTENANCE_STARTUP_TIMEOUT_MS=120000
```

В том же хранилище gateway сохраняет публичные файлы `/_next/static` каждого
установленного образа. Они остаются доступны по прежним адресам, чтобы открытая
вкладка смогла догрузить свой интерфейс после смены версии. Эти файлы разрешены
только на чтение даже во время обслуживания; страницы и API остаются закрытыми.
Архив не содержит пользовательских данных и автоматически не удаляется. При
первой установке файлы прежнего образа ещё не архивированы: безопасное
догрузку старого интерфейса обеспечивает только архив уже установленных через
этот gateway версий. Изменения API и миграции всё равно должны сохранять
совместимость с открытыми вкладками.

В Coolify для этого приложения установить:

- **Pre-deployment command:** `node scripts/maintenance-control.mjs on`
- **Post-deployment command:** `node scripts/maintenance-control.mjs off`
- **Stop Grace Period:** минимум `180` секунд при указанном таймауте `120000`.
- **Healthcheck:** существующий `/api/health`, внутренний порт `8080`.

`on` атомарно закрывает доступ и ждёт завершения всех принятых запросов в текущем
контейнере. Только код выхода `0` разрешает следующий шаг. Ошибка или таймаут
оставляют режим включённым; деплой продолжать нельзя. Команды нельзя оборачивать
в `|| true`. Новый контейнер должен начинать миграции только после успешного
завершения pre-command старого. Эта схема рассчитана на один текущий экземпляр;
при нескольких репликах сначала требуется завершить запросы каждого экземпляра.

`off` проверяет готовность приложения и затем снимает переключатель. При ошибке
доступ остаётся закрытым. `/api/health` продолжает возвращать `200`, когда backend
и БД готовы, даже при ручном обслуживании; публичный
`/api/maintenance/status` показывает фактический доступ пользователей.

При первой установке этой функции прежний образ ещё не содержит команд
`maintenance-control.mjs`. Назначать pre-command до установки такого образа
нельзя. Первое обновление провести отдельно после завершения текущих сохранений,
используя maintenance mode **только этого ресурса** в Coolify; затем настроить
постоянное хранилище и обе команды для следующих деплоев.

Для других плановых работ те же команды запускаются в Terminal текущего
контейнера: сначала `on`, после завершения работ и проверки БД — `off`.
`MAINTENANCE_MODE=true` принудительно закрывает доступ; снять его командой `off`
нельзя, требуется изменить переменную и перезапустить приложение.

SIGTERM закрывает новые запросы и ждёт уже начатые перед остановкой backend.
Принудительное завершение Docker/хоста в обход grace period этого не гарантирует.
Фоновые задачи и прямые подключения к БД не проходят через HTTP gateway; перед
несовместимыми миграциями их также останавливают отдельно.

### Страница при отсутствии контейнера приложения

Gateway не может отвечать, когда самого контейнера нет. Для этого подготовлены
независимый контейнер без доступа к БД и доменная конфигурация Traefik:

- `ops/maintenance/compose.yml` и `ops/maintenance/Dockerfile`;
- `ops/maintenance/traefik.yml`;
- автономная страница `public/maintenance.html` (генерируется при сборке).

Fallback запускается отдельно от деплоя приложения на существующем сервере,
в его сети Coolify, без `ports:`. Перед подключением проверить версию Traefik,
имена `http`/`https`, resolver `letsencrypt` и выбранную Docker-сеть. В Dynamic
Configurations добавить подготовленный YAML. К **существующим** middleware
роутеров этого приложения добавить `personnel-maintenance-errors@file`, сохранив
их TLS, redirects и остальные middleware. Не заменять все labels приложения и
не включать глобальную страницу ошибок сервера: она затронет другие проекты.

Coolify может преобразовать `errorRequestHeaders: []` в `{}` при сохранении
Dynamic Configuration. Поэтому `personnel-maintenance-errors` в подготовленном
YAML — цепочка: сначала удаляется служебный заголовок
`X-Personnel-Maintenance-Request`, затем errors middleware разрешает передать
только его. Непустой список сохраняет правильный тип, а исходные заголовки,
включая `Cookie` и `Authorization`, не передаются обработчику ошибок. Порядок
двух middleware менять нельзя; отсутствие `errorRequestHeaders` разрешает
пересылку всех заголовков.

Роутеры с приоритетом `1` ограничены двумя указанными доменами и отвечают, если
маршрут приложения отсутствует. Middleware обрабатывает `502–504` при недоступном
backend. API получает JSON, страницы — HTML. Исходные URL, cookies и токены
приглашений не отражаются в ответе и не записываются в логи fallback.
При остановке всего сервера или его proxy этот контейнер тоже не сможет ответить.

Для fallback задать `PERSONNEL_STATIC_ARCHIVE`: абсолютный путь на сервере к
каталогу `static` внутри постоянного хранилища приложения. Compose монтирует
только этот публичный каталог read-only, а не весь `/app/.runtime`.
Оба процесса работают с UID/GID `1001:1001`, что позволяет читать архив с
ограниченными правами. Отдельный HTTPS-роутер `/_next/static/` с приоритетом
`2000` отдаёт сохранённые файлы с `200` даже между контейнерами. Неизвестные
файлы получают `404`; этот маршрут не открывает страницы или API. Включать его
после заполнения архива текущей установленной версии, чтобы не перекрыть ещё
неархивированные файлы старого образа.

### Установка fallback из уже работающего образа

Если установленный образ уже содержит gateway и публичный архив, новый build
не нужен. Для этого конкретного приложения подготовлен
`ops/maintenance/install-existing-image.sh`. В root-terminal существующего
сервера сначала загрузить в каталог
`/data/coolify/applications/qmwx1es9ldj6oz0pdrtsgkk6/maintenance-fallback`
сам installer и файлы `scripts/maintenance-fallback.mjs`,
`scripts/maintenance-assets.mjs`, сохраняя подкаталог `scripts`. Секреты и
файлы окружения в этот bundle не копируются. Затем выполнить:

```bash
bash /data/coolify/applications/qmwx1es9ldj6oz0pdrtsgkk6/maintenance-fallback/install-existing-image.sh
```

Installer выбирает ровно один работающий контейнер с префиксом UUID приложения,
использует его локальный image ID с `--pull=never` и отдельной командой Node.
Он копирует текущий автономный HTML и безопасно объединяет публичный архив,
создаёт приватный fallback в сети `coolify` без опубликованных портов и доступа
к БД. Проверка здоровья fallback выполняется на `8099`, отдельно от healthcheck
приложения на `8080`. Несовпадающий существующий fallback не заменяется и не
останавливается; неоднозначный выбор во время rolling update прерывает setup.

Хранилище этого варианта —
`/data/coolify/applications/qmwx1es9ldj6oz0pdrtsgkk6/maintenance-runtime`, его
нужно назначить приложению на `/app/.runtime`. Сохранённый в UI mount вступит
в силу при следующем деплое. Installer включает переключатель только в новом
неиспользуемом каталоге (или пустом каталоге без mount у текущего контейнера),
чтобы первый новый контейнер дождался post-command. Существующее состояние
не сбрасывается; работающий контейнер и его данные не изменяются.

Hooks, mount, stop grace period и доменные правила proxy настраиваются отдельно;
installer не включает технические работы у пользователей и не запускает
деплой. Последующие версии gateway пополняют общий статический архив, который
fallback читает через mount, поэтому пересобирать его при каждом деплое не
нужно. Изменение самого экрана или fallback-скриптов требует отдельного
контролируемого обновления; installer намеренно откажется заменять отличающийся
контейнер. Локальная проверка installer или YAML не применяет настройки Coolify.

После подключения проверить на тестовом окне: ввод в ячейке → `on` → новые
сохранения отклонены, принятые завершены → замена контейнера → `off` → ввод на
месте, рабочая страница доступна. Отдельно проверить первую загрузку сайта,
когда контейнер приложения остановлен. Эти серверные настройки автоматически
не применяются запуском локальных тестов или отправкой кода.
